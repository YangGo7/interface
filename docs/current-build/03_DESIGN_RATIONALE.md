# 현재 빌드 설계 이유

이 문서는 코드를 왜 이렇게 작성했는지 정리한 문서다.

설계 이유는 추측으로 쓰지 않았음. 현재 코드 구조와 현재 기능이 요구하는 책임을 기준으로 정리했음.

## 1. 왜 화면을 3단계로 나눴는가

`FolderLeaderVer2Page -> RenewPage -> WebReportPage`로 나눈 이유는 책임을 분리했기 때문이다.

- 검사 찾기와 업로드는 입력 단계다.
- 뷰어는 검토와 캡처 단계다.
- 리포트는 편집과 버전 관리 단계다.

이 3개를 한 화면에 합치면 상태가 섞이고 유지보수가 어려워진다.

현재 코드는 단계별 상태를 분리했기 때문에 아래 이점이 생겼다.

- 업로드 로직이 리포트 편집 상태를 오염시키지 않는다.
- 리포트 버전 로직이 뷰어 상태와 섞이지 않는다.
- 화면별 테스트 범위를 명확하게 나눴다.

## 2. 왜 `Upload Image`와 `Upload Folder`를 분리했는가

브라우저 파일 선택 동작이 다르기 때문에 분리했음.

- 이미지 선택은 단일 파일 흐름이다.
- 폴더 선택은 다중 파일을 읽고 DICOM 묶음을 만들어야 한다.

현재 코드는 아래처럼 처리 경로가 다르다.

- `handleLocalFilePick`는 파일 하나를 바로 `/renew`로 넘긴다.
- `handleLocalFolderPick`는 `buildDicomFolderStudies`를 거쳐 study와 series를 구성한 뒤 `/renew`로 넘긴다.

버튼을 나누면서 아래 문제가 같이 해결됐음.

- 업로드 의미가 명확해졌음.
- 사용자가 파일과 폴더를 헷갈리지 않게 됐음.
- 코드도 두 흐름을 억지로 합치지 않게 됐음.

## 3. 왜 서버 목록 API와 브라우저 내부 파싱을 같이 두었는가

입력 소스가 2개라서 같이 두었음.

- 서버 폴더를 읽을 때는 백엔드가 파일 시스템을 직접 스캔한다.
- 사용자가 로컬 폴더를 선택할 때는 브라우저가 받은 `File[]`를 직접 파싱한다.

이 구조를 택한 이유는 아래와 같음.

- 서버 폴더 접근은 브라우저가 직접 할 수 없다.
- 로컬 선택 파일은 서버로 다 올리지 않고 브라우저에서 바로 묶는 편이 더 빠르다.

현재 코드에서 이 역할은 아래처럼 갈렸다.

- 서버 경로는 `dicom_server_browser.py`가 담당한다.
- 브라우저 로컬 폴더는 `buildDicomFolderStudies`가 담당한다.

## 4. 왜 `Studies` 목록에서 study와 image를 함께 다루는가

사용자 작업 기준으로 보면 둘 다 "열어야 하는 대상"이기 때문이다.

예전처럼 study와 image를 탭으로 나누면 아래 문제가 생긴다.

- 사용자가 어디에 들어 있는지 기억해야 한다.
- 이미지 상태에서 다시 DICOM study로 바꾸는 흐름이 길어진다.
- 상단 UI가 불필요하게 복잡해진다.

현재 빌드는 `Studies` 하나로 통합했고 `Images` 버튼을 제거했음.

이렇게 한 이유는 아래와 같음.

- 선택 진입점을 하나로 줄였음.
- `RenewPage`에서도 study와 image를 같은 패널에서 바꾸게 했음.
- 서버 이미지 상태에서 `Studies`를 눌렀을 때 다른 image와 DICOM을 함께 보이게 했음.

## 5. 왜 뷰어 안에서 서버 study를 다시 materialize 하는가

서버 목록 응답은 메타데이터 중심이고, 뷰어는 실제 `File` 객체 묶음이 필요하기 때문이다.

현재 구조는 아래 두 단계를 쓴다.

1. 목록에서는 가벼운 메타데이터를 사용한다.
2. 실제 열 때만 `materializeServerStudy`로 파일을 내려받아 `FolderStudy`를 만든다.

이 설계가 필요한 이유는 아래와 같음.

- 목록 단계에서 모든 DICOM 파일을 다 내려받으면 느려진다.
- 열지 않는 검사까지 미리 전부 materialize 하면 낭비가 커진다.
- 뷰어 쪽 타입은 `FolderStudy`로 통일되어 있다.

즉 현재 코드는 "목록은 가볍게, 열 때 무겁게"라는 규칙으로 작성했음.

## 6. 왜 리포트 저장을 서비스로 나눴는가

`web_report.py`에서 DB 저장, 결과 병합, 문서 생성을 한 파일에 다 넣지 않기 위해 나눴다.

현재 책임 분리는 아래와 같음.

- `WebReportSessionService`
  - SQLite 읽기와 쓰기를 담당한다.
- `WebReportMergeService`
  - AI 결과와 의사 override를 병합한다.
- `WebReportReportService`
  - HTML/PDF 생성 책임을 가진다.

이렇게 나눈 이유는 아래와 같음.

- DB 변경과 병합 규칙 변경과 문서 생성 변경은 수정 이유가 다르다.
- 하나의 파일에 책임을 몰아넣으면 버전 복원 같은 기능이 깨지기 쉽다.
- 서비스 단위로 보면 리포트 문제를 추적하기 쉬워진다.

## 7. 왜 AI 결과와 override를 분리 저장하는가

AI 원본과 사람 수정값의 목적이 다르기 때문이다.

- AI 결과는 최초 분석 결과다.
- override는 사람이 바꾼 결과다.

이 둘을 섞어서 한 번에 저장하면 아래 문제가 생긴다.

- 어떤 값이 AI 원본인지 추적이 안 된다.
- 과거 버전 복원이 어려워진다.
- 리포트 재생성 시 기준점을 잃는다.

현재 코드는 아래 방식으로 분리했음.

- `web_report_ai_results`에 AI 원본 저장
- `web_report_doctor_overrides`에 사용자 수정 저장
- `WebReportMergeService`가 둘을 합쳐 `effective_result`를 만든다

이 방식 때문에 복원과 재생성이 안정적으로 동작한다.

## 8. 왜 버전 복원을 HTML 교체가 아니라 스냅샷 복원으로 구현했는가

리포트는 HTML 파일만 바꾸면 끝나는 구조가 아니기 때문이다.

리포트 화면은 아래 값을 같이 맞춰야 한다.

- 치아별 포함 여부
- 질환 체크 상태
- bone loss 값
- report note
- 첨부 capture
- 현재 선택 버전

그래서 현재 코드는 아래처럼 작성했음.

1. 버전 생성 시 `snapshot_json`을 저장한다.
2. 복원 시 `snapshot_json`을 읽는다.
3. `build_overrides_from_snapshot`로 override를 다시 만든다.
4. `current_report_version`도 같이 갱신한다.

이 방식 덕분에 화면 상태와 저장 상태가 다시 일치한다.

## 9. 왜 `current_report_version` 컬럼을 따로 두었는가

세션이 "지금 무엇을 기준으로 보여주고 있는지"를 명확히 저장해야 하기 때문이다.

버전 테이블만 보면 아래 문제를 해결할 수 없다.

- 가장 최근에 생성된 버전과 현재 사용자가 보고 있는 버전이 다를 수 있다.
- 복원 직후 어떤 버전이 현재 기준인지 따로 기억해야 한다.

그래서 세션 테이블에 `current_report_version`을 따로 두었음.

이 값은 아래 시점에 중요하다.

- 리포트 화면 첫 로딩
- 프리뷰 URL 생성
- 버전 복원 직후 화면 재구성
- 최종 리포트 저장

## 10. 왜 캡처를 별도 상태와 override로 다루는가

캡처는 단순 화면 장식이 아니라 리포트 자산이기 때문이다.

현재 코드는 아래처럼 분리했다.

- `capturedOutputs`가 뷰어 내부 캡처 목록을 가진다.
- 선택한 캡처만 `attached_captures`로 리포트 세션에 동기화한다.

이렇게 한 이유는 아래와 같음.

- 모든 캡처를 무조건 리포트에 넣지 않게 했음.
- 뷰어 캡처 생성과 리포트 첨부를 분리했음.
- 캡처 note를 리포트 쪽 상태로 관리하게 했음.

## 11. 왜 릴리스 빌드를 스크립트로 묶었는가

이 프로젝트는 프론트엔드 정적 파일만 복사해서 끝나는 구조가 아니기 때문이다.

배포에 필요한 것은 아래와 같음.

- 프론트엔드 `dist`
- 백엔드 코드
- 모델 관련 폴더
- 실행 스크립트
- `.env`
- 빈 데이터 폴더

그래서 `build_release.ps1`이 아래 일을 한 번에 한다.

- 프론트엔드 빌드
- 패키지 폴더 생성
- 프론트 복사
- 백엔드 디렉터리 복사
- 실행 스크립트 포함
- zip 생성

이 구조를 택한 이유는 다른 PC 설치를 반복 가능하게 만들기 위해서다.

## 12. 이 문서가 필요한 대상

- 왜 이런 구조를 택했는지 설명해야 하는 개발자에게 맞췄다.
- 기능 추가 전에 기존 규칙을 파악해야 하는 유지보수 담당자에게 맞췄다.
- 리팩터링 전에 책임 경계를 확인해야 하는 사람에게 맞췄다.
